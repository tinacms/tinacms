Why graphql-pipeline.ts exists

One sentence: it is the adapter that lets v4's local data layer answer GraphQL queries by driving the existing v3 engine (@tinacms/graphql) without rewriting a query engine, an indexer, or a resolver.

The problem it solves

The v4 admin queries content with GraphQL (query() in the content contract). Answering GraphQL over a folder of markdown/json files needs three things: a schema built from the collections, an index of every document (so list queries, filters and references don't re-read the filesystem per query), and a resolver that executes queries against that index.

All three already exist, battle-tested, in @tinacms/graphql — but that package speaks the v3 schema shape and expects a LevelDB-style store plus a "bridge" to the filesystem. v4 has its own, flatter CollectionSchema. Something has to sit between them. That something is this file, and only this file: the rest of v4 never touches @tinacms/graphql.

v4 CollectionSchema → toV3Collection / toV3Field → buildDotTinaFiles → indexContent → sqlite-level (:memory:) → resolve(query)

What each piece is for

PieceWhy it's there
toV3Field / toV3Collection Translate v4 schema to the v3 shape the engine expects. Kept minimal on purpose: only the fields the engine actually reads.
SqliteLevel(':memory:') The engine needs a Level store for its index. In-memory sqlite = zero files on disk, fresh index per dev-server boot, injectable (options.level) for tests.
FilesystemBridge How the engine reads the actual content files under rootDir.
buildDotTinaFiles(... buildSDK: false) Builds the GraphQL schema + lookup tables from the collections, without generating the client SDK files v3 would write to disk.
reindexPaths + the indexing promise chain When a file changes (a save), only that path is re-indexed. The chain serialises re-index runs so two rapid saves can't interleave index writes; a failed run doesn't poison the next (.catch(() => {})).
warnUnindexedFormats Honest limitation, stated up front: a collection with several formats indexes the first only; the rest stay editable but invisible to queries.

Why not something simpler?

  • Scan files per query? Works for 10 documents, dies on reference resolution, filtering and pagination — exactly what the v3 engine's index already does.
  • Rewrite a small engine in v4? That's re-owning schema building, indexing and resolving — thousands of lines of proven code for zero product gain.
  • Use v3's full stack directly? It drags in the .tina file generation, SDK output and server assumptions v4 doesn't want. This file cherry-picks the four functions needed and nothing else.

So: ~95 lines of adapter buys the whole v3 query engine, contained behind a three-method interface (execute, reindexPaths, close). When ADR work replaces the engine, this is the only file that changes.
